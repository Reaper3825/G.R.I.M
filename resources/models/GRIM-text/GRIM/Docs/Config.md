# Configuration (`ai_config.json`)

All model and training configuration lives in `ai_config.json`.

Intended cleanup target: config handling is split into exactly three layers:

- `control/ai_config_paths.hpp` owns the single strict snapshot load operation. It exposes one raw loader (`loadAiConfigSnapshot`), and `AiConfigSnapshot` is the only custom type defined there. The loader must not define field-wrapper structs, pointer-member schema tables, split validators, pre-Phase1 helper operations that mirror the JSON schema, or a caller-supplied config-path override branch. It loads the canonical `ai_config.json` into `AiConfigSnapshot::{config_path, document}` and fails loud on invalid JSON. Missing authored JSON fields fail at the immediate HyperParameters handoff — never via optional parsing or fallback defaults. `AiConfigSnapshot` must not contain flat leaf mirrors, `TrainingHyperparameters`, `LanguageModelConfig`, `GenerationConfig`, log-recorder/tape config structs, architecture structs, enum-parsed precision, or any other downstream typed config owner. GRIM process-owned fields such as `data_collection.max_new_entries_per_run` are not typed GRIM-text leaves; their process consumers own those reads.
- `Shared/HyperParameters/HyperParameters_GPU.hpp` owns the first authoritative typed config structs, derivation, validation, and final durable config handoff (`TrainingHyperparameters`, `LanguageModelConfig`, `StartupConfig`, etc.). `TrainingHyperparameters` is not a `LanguageModelConfig` wrapper and must not inherit from or contain a `LanguageModelConfig`/`architecture` subobject. `loadTrainingHyperparameters()` is the boundary that reads flat `training.config` leaves from `AiConfigSnapshot::document`, parses enum/string policies, builds nested logging structs, validates cross-field policy, and computes formula-derived values. `StartupConfig` resolves `training.config.grim_text_*` path leaves there as well. Downstream model config objects are explicit handoffs derived from that owner. `loadModelArchitecture()` derives from `TrainingHyperparameters`, and `loadGenerationConfig()` reads `training.config.generation_*` leaves into `GenerationConfig`. Neither `TrainingHyperparameters::generation` nor `AiConfigSnapshot::generation` wrapper objects are allowed.
- `Shared/HyperParameters/HyperparameterGroupings.hpp` owns immutable grouped read views used by phase code. It must not include or call `ai_config_paths.hpp` directly, it must not own authored defaults/constants, and it may only slice/derive from finalized `HyperParameters_GPU.hpp` structs and constants. Phase 1 authors exactly one static model config set (`TrainingContext.model_config`) via `startupLanguageModelConfig()`; model construction receives it once, `LanguageModel` stores its own copy, and Phase 2 consumes `ctx.model_config` directly. Do not rebuild, forward-declare, or route alternate static model config wrappers through registration/training paths. Server/runtime inference uses `inferenceLanguageModelConfig()`.

`HyperparameterGroupings.hpp` must never be wrapped, mirrored, or forward-declared from consumer files. If a subsystem needs a grouping type, include `HyperparameterGroupings.hpp` and accept the explicit grouping payload. If a subsystem already receives the actual config (`LanguageModelConfig`, `TrainingHyperparameters`, or `StartupConfig`), do not pass a second sidecar policy/config beside it. Put authored fields on the actual config owner, let `AiConfigSnapshot` remain a raw authored snapshot instead of a second config owner, slice finalized values through an existing grouping only when needed, and have the consumer read one authoritative source. GRIM process-level fields such as `data_collection` are not GRIM-text model/training fields and must not be copied into training/inference startup config or typed snapshot leaves. Config access helpers/facades must live only in `HyperParameters_GPU.hpp` or `HyperparameterGroupings.hpp`; every other file consumes typed config/grouping payloads passed to it instead of reaching through another module. This is especially important for `ParameterGroupRegistration`: precision/type metadata is stamped on registered `ParameterGroup` entries from the model's actual `LanguageModelConfig`, not from a parallel policy object.

`startupLanguageModelConfig()` is also the single policy boundary that stamps training startup models with `ModelExecutionMode::TRAINING`. `inferenceLanguageModelConfig()` is the matching boundary for server/runtime inference and stamps `ModelExecutionMode::INFERENCE` plus the single-row prompt/cache capacity. Do not rely on the `LanguageModelConfig` default (`INFERENCE`) in training code; training `BatchPayload` upload is forbidden for inference-mode models.

Startup TrainingState cache capacity is authored on the HyperParameters-owned config surface and handed off onto `LanguageModelConfig` as the values the allocator actually consumes: `max_cached_batch` and `max_tokens_per_batch`. `validateLanguageModelCacheCapacity()` validates those consumed capacities when startup/inference configs are produced, and `TrainingState::allocateStepDeviceWorkspaces()` validates the same authored config before allocating reusable tensors. `max_cached_seq_len` belongs to prompt/KV/payload capacity paths, not the TrainingState token-cache validation path. Fixed-shape training geometry (`batch_size`, `max_seq_len`, checked `max_tokens_per_batch`) is HyperParameters/HyperparameterGroupings-owned config via `trainingFixedShapeHP()`, and is enforced at the upload boundary; prompt/decode inference geometry remains explicit runtime payload data.

`BatchPayload` materializes per-batch/per-prompt data and realized runtime geometry: token IDs, targets, sequence lengths, numeric values, atom metadata, slot maps, and current valid-token counts. In fixed-shape training/eval it must match the HyperParameters/HyperparameterGroupings-authored model geometry already handed off through `LanguageModelConfig`; config/grouping code still owns the static startup values and must not absorb prompt contents or other current batch facts.

Mixed precision is configured once at startup via flat `training.config.parameter_precision_*` leaves. These authored strings are read by `loadTrainingHyperparameters()` from the raw snapshot document, parsed there, and copied into the explicit `LanguageModelConfig` handoff as per-parameter-group precision values. `ParameterGroupRegistration` is the durable handoff: it validates the authored values, stamps each registered `ParameterGroup`, and stamps the owning `Tensor`'s TensorContract precision metadata. `LanguageModelConfig` does not own a model-wide precision mode, and there is no sidecar precision policy. Runtime TensorContract operators consume tensor metadata; raw FP32↔BF16 conversion kernels belong only in `Shared/TensorConversion`. A `bf16_compute` request must fail during registration until the matching TensorContract compute consumer is wired, never silently run as FP32.

Phase/startup code may consume grouped views for subsystem construction, loss, tokenizer, optimizer, and payload-specific contracts, but static model configuration itself is not wrapped: no `ModelArchitectureHP`, no `ParameterRegistrationHP`, and no alternate architecture mirror. If Phase2/diagnostics need static model fields, read `TrainingContext.model_config` directly. If a new startup subsystem needs a repeated non-static slice of config, add that view to `HyperparameterGroupings.hpp`; if it needs a new authored field/default/constant, add that to `HyperParameters_GPU.hpp` first. Do not create a third config owner. Loss runtime config follows this rule through `LossConfigHP` / `lossConfigHP()`: startup/Phase2 consumers derive the explicit grouping from authoritative `TrainingContext.config.hyperparameters` at the boundary that needs it, instead of storing a second `TrainingContext.loss_config` owner. `LossConfigHP` has no runtime `initialized` sentinel; validity belongs to hyperparameter validation plus the explicit `lossConfigHP()` derivation boundary. `TrainingContext`, `TrainingLoopState`, `AutogradContext`, and `LanguageModel` must not store, rebuild, revalidate, or mutate a separate loss-config owner.

Tokenizer startup/build paths consume `TokenizerHP` / `tokenizerHP()` directly. `TokenizerHP` carries the resolved tokenizer artifact paths (`data_path`, `vocab_path`), rebuild policy (`force_rebuild_vocab`), and tokenizer settings; do not pass `StartupConfig.paths`, `PathConfig`, rebuild booleans, or a tokenizer-artifact path wrapper as a second tokenizer payload. `UniByte` stores that grouping as its tokenizer HP snapshot; `train_tokenizer`, `DataLoader`, `LoadTrainingData`, `tokenizer_runner`, and `tokenizer_self_test` must not hand-build a separate tokenizer config mirror from raw snapshot fields, ad-hoc JSON reads, or scattered `StartupConfig` leaves. Tokenizer authored values belong under the single `training.config` parse boundary, land on `TrainingHyperparameters`, and are sliced directly into `TokenizerHP`; do not add `StartupConfig::tokenizer_*` mirrors back. Direct tokenizer leaves include `tokenizer_vocab_size`, `tokenizer_max_vocab_size`, `tokenizer_max_length`, `tokenizer_character_coverage`, `tokenizer_min_cleaned_text_length`, `tokenizer_min_subword_freq`, `tokenizer_prune_during_mining`, `tokenizer_enable_parallel_subword_mining`, `tokenizer_subword_mining_workers`, `tokenizer_subword_mining_max_bytes`, `tokenizer_model_type`, `tokenizer_add_bos`, `tokenizer_add_eos`, `tokenizer_unk_token`, `tokenizer_pad_token`, `tokenizer_bos_token`, `tokenizer_eos_token`, `tokenizer_enable_nfkc_normalization`, `tokenizer_enable_lowercasing`, `tokenizer_enable_parallel_tokenization`, `tokenizer_parallel_threshold`, `tokenizer_enable_byte_fallback`, `tokenizer_expected_checksum`, `tokenizer_save_text_vocab`, `tokenizer_vocab_score_multiplier`, `tokenizer_special_tokens`, `tokenizer_enable_scratch_block_reasoning`, and `tokenizer_detect_numbers`; do not recreate nested `training.config.tokenizer.*` fields. `LoadTrainingData()` consumes `DataLoadingHP` for data-loading policy and reads the configured `StartupConfig.max_seq_len` directly for sliding windows; do not reintroduce a local data-load input wrapper or a capacity grouping that just mirrors config fields. Isolated tokenizer tests construct explicit `TokenizerHP` fixtures instead of a wrapper struct.

Subprocess coordinator code follows the same single-root rule: Phase 1 loads config once, `HyperParameters_GPU.hpp` consumes the raw snapshot document, derives an explicit subprocess grouping from finalized config in `HyperparameterGroupings.hpp`, and passes that grouped snapshot into `training/Subprocess/`. The authored JSON leaf `training.config.subprocess_tokenizer_only_mode` is required in `ai_config.json`, is loaded onto `TrainingHyperparameters::subprocess_tokenizer_only_mode`, and is then sliced into `TokenizerSubprocessHP::only_mode`. `TokenizerSubprocessHP` must not carry `config_path`; subprocess launch consumes tokenizer-owned artifact paths plus the grouped flag only. Do not reparse `ai_config.json` inside `training/Subprocess/`, do not read raw snapshot leaves there, and do not hand-build fake argv/startup wrappers just to recover tokenizer paths or subprocess flags.

`training.config.tokenizer_min_cleaned_text_length` owns the minimum rendered/cleaned text byte length required before `DataLoader.cu` encodes a concept/plaintext row into GRMT. Keep this threshold in `ai_config.json`, load it into `TrainingHyperparameters`, and slice it into `TokenizerHP`; do not reintroduce a file-local DataLoader constant.

`training.config.tokenizer_character_coverage` is authored tokenizer policy. It must flow through `TrainingHyperparameters::tokenizer_character_coverage` directly into `TokenizerHP::character_coverage`; do not reintroduce `StartupConfig::tokenizer_character_coverage` or a `TOKENIZER_CHARACTER_COVERAGE` constexpr in `HyperParameters_GPU.hpp`.

`training.config.guess_aux` has been removed. The downstream GuessCache/guess-aux config gating path is no longer part of the training config contract, so do not require, parse, dump, or registry-expose `guess_aux.enabled`, `guess_aux.lambda`, or `guess_aux.min_confidence`.

ExecutionBlock runtime policy values such as `execution_block_num_scratch_slots`, value-decode dimensions, inject-gate temperature, result-slot policy, debug mode, collapse thresholds, magnitude limit, and decode-time selector feature dimensions are collapsed direct leaves under `training.config`. ExecutionBlock leaves use the `execution_block_*` prefix, and selector leaves use the `selector_*` prefix; do not recreate nested `training.config.execution_block` or `training.config.execution_block.selector` sidecar objects. They are loaded by `HyperParameters_GPU.hpp::loadTrainingHyperparameters()` from the raw snapshot document, copied into the explicit `LanguageModelConfig` handoff, and sliced by `executionBlockConstructionHP()` / `decodeTimeSelectorConstructionHP()`. Do not reintroduce `EXECUTION_BLOCK_*` or `DECODE_TIME_SLOT_FEATURE_DIM` constexpr defaults for those runtime knobs. Kernel launch constants like FlashAttention tile sizes remain compile-time constants.

Scheduler/control leaves selected from early `training.config` are collapsed direct leaves as well. Cosine decay uses `cosine_decay_enabled` and `cosine_warm_restarts`; auto-stop uses `auto_stop_*`; CUDA execution uses `single_stream_mode`, `disable_async_frees`, and `synchronize_after_kernels`; embedding freeze uses `embedding_freeze_enabled` and `embedding_freeze_after_step`; attention diagnostics uses `attention_diag_*`. Do not recreate nested sidecar objects such as `cosine_decay`, `auto_stop`, `cuda_execution`, `embedding_freeze`, or `attention_diagnostics` for these fields. UI/config writer paths must write the same flat leaves the loader requires.

Generation, LM-head centering, LayerScale, hardcoded hidden-state diagnostics, and log-recorder startup policy are also collapsed direct leaves under `training.config`. Generation uses the `generation_*` prefix and is converted to `GenerationConfig` only by `HyperParameters_GPU.hpp::loadGenerationConfig()`; do not add `TrainingHyperparameters::generation`, `AiConfigSnapshot::generation`, or any other generation wrapper root. Hardcoded hidden-state diagnostics use `hardcoded_hidden_states_enabled`, `hardcoded_hidden_states_pattern`, and `hardcoded_log_every_n_batches`; LM-head centering uses `lm_head_centering_enabled`, `lm_head_center_hidden_states`, `freeze_learned_rms_gammas`, `center_logits`, `center_encoder_residuals`, `project_out_pc1`, and `pc1_power_iters`; LayerScale uses `use_layer_scale` and `layer_scale_init`; log recorder uses `log_recorder_enabled`, `log_recorder_default_level`, direct `log_recorder_layer_*` booleans, and the direct `log_recorder_modules` object. Do not recreate nested sidecar objects such as `generation`, `hardcoded_hidden_states`, `lm_head_centering`, `layer_scale`, or `log_recorder` for these fields.

Tape logging, logit-update tracing, loss policy, MTP policy, and optimizer policy are collapsed direct leaves under `training.config`. Tape logging uses `logging_default_level`, `logging_equation_csv_enabled`, `logging_stderr_enabled`, `logging_initial_capacity`, and the direct `logging_group_overrides` object. Logit tracing uses `logit_update_trace_enabled` and `logit_update_trace_interval`. Loss uses direct `loss_*` leaves, MTP uses direct `mtp_*` leaves, and optimizer uses direct `optimizer_*` leaves. Do not recreate nested sidecar objects such as `logging`, `logit_update_trace`, `loss`, `multi_token_prediction`, or `optimizer` for these fields; UI/config writer paths must write the same flat leaves the loader requires.

`setDefaultHyperparameters()`, `validateAiConfigDocument()`, `appendMissingTrainingConfigPaths()`, and field-table validators have been removed from `ai_config_paths.hpp`. The raw config layer only loads `AiConfigSnapshot::{config_path, document}`. `TrainingHyperparameters` is value-initialized and populated only by `HyperParameters_GPU.hpp::loadTrainingHyperparameters()`. Formula-derived values are computed by `HyperParameters_GPU.hpp` via `deriveComputedTrainingHyperparameters()`. Do not add a new pre-parse defaulting pass, side validator, or schema table; add authored runtime fields to `ai_config.json` and the HyperParameters typed load instead, or derive them in HyperParameters when they are pure formulas.

Flat `training.config.stability_override_*` leaves are authored runtime policy, not a hidden derivation. The loader requires `stability_override_batch_size`, `stability_override_max_seq_len`, and `stability_override_clip_per_token`, and `stability_overrides_enabled` only decides whether those authored values are applied at startup. Do not regenerate override payloads from `batch_size`, `max_seq_len`, or magic constants inside `deriveComputedTrainingHyperparameters()`.

Flat `training.config.telemetry_*` leaves are the authored telemetry contract. Telemetry leaves such as `telemetry_spike_mild_threshold`, `telemetry_moderate_grad_scale`, `telemetry_min_grad_for_nonzero_loss`, `telemetry_plateau_noise_enabled`, and `telemetry_lattice_num_levels` live directly under `training.config`; do not recreate nested sidecar groups such as `telemetry_control`, `spike_thresholds`, `response`, `accumulation_guard`, `plateau_noise`, or `lattice`. `loadTrainingHyperparameters()` reads each telemetry leaf from the raw snapshot document and builds the finalized training owner.

`training.config.scratch_block_atom_embedding_dim` is authored config and must survive the parse boundary unchanged. Do not recompute it from `d_model` in post-parse derivation.

`LanguageModel` owns only `LanguageModelConfig` plus runtime/model state. It must not retain `TrainingHyperparameters` pointers or expose pass-through accessors for Phase 1 config. After `TrainingContext.model_config` is authored, Phase2 and diagnostics must consume that handoff directly instead of reading removed hyperparameter architecture subobjects or rebuilding static model groupings.

Grouped construction views also own repeated derived dimensions for their consumers. For encoder construction, `EncoderLayerConstructionHP` carries validated GQA/QKV dimensions (`head_dim`, `heads_per_kv_group`, `kv_dim`, `qkv_dim`, `is_gqa`) so layer code does not recompute config geometry locally.

PBM positional encoding construction uses `PBMConstructionHP` from `HyperparameterGroupings.hpp`. `Shared/PBM/PositionalBiasMethod.*` consumes that grouped view plus explicit runtime options only; it must not define its own authored defaults or hand-copy `LanguageModelConfig` fields.

Flat `training.config` PBM leaves own both the encoding mode and PBM tuning knobs. The required authored fields are `use_rope`, `use_alibi`, `rope_base_seq_len`, `alibi_min_locality_distance`, `alibi_slope_exponent`, `alibi_max_bias`, `rope_theta`, and `rope_scaling`. `HyperParameters_GPU.hpp::loadTrainingHyperparameters()` reads those values from the raw snapshot document into the finalized typed surface, and `pbmConstructionHP()` slices finalized values into `PBMConstructionHP`. Do not reintroduce `DEFAULT_POSITIONAL_ENCODING`, `ROPE_BASE_FREQ`, `ROPE_THETA`, `ROPE_SCALING`, `ROPE_BASE_SEQ_LEN`, `ALIBI_SLOPE_EXPONENT`, `ALIBI_MIN_LOCALITY_DISTANCE`, or `ALIBI_MAX_BIAS` constants; those are authored config, not math constants.

Encoder-facing autograd helpers consume grouped attention snapshots sliced from `EncoderLayerConstructionHP` (`EncoderSelfAttentionHP`). Encoder files must not build local `TensorContract::GQADims` wrappers or store encoder-owned GQA snapshots; the grouped HP snapshot is the source for Q/K/V geometry.

Layer classes may store a durable copy of their grouped construction view when forward/runtime methods need the values after startup-local grouping objects are destroyed. Name those members as HP/grouping snapshots (for example `hp_`), not as authored config owners, and keep borrowed tensor ownership outside the grouping. Forward-time runtime handles (`cudaStream_t`, `cublasHandle_t`) belong to per-call payload/request structs, not layer configs or late mutator methods; startup constructors may take an init stream only for allocation.

ScratchBlock startup construction uses `ScratchBlockConstructionHP` / `scratchBlockConstructionHP()`. That grouping owns static values such as `d_model`, `scratch_block_max_atoms`, `scratch_block_atom_embedding_dim`, atom token range, and `scratch_block_atom_scale`. It must not own the CUDA stream; `ModelGpuAssembly.cu` supplies the startup init stream when constructing `ScratchBlockLayer`.

RMSNorm shape/epsilon travels through the same grouped construction HP as the owning layer (`EncoderLayerConstructionHP::rms_epsilon`, `LMHeadLayerConstructionHP::rms_epsilon`). Runtime CUDA streams and gamma tensor ownership stay outside the grouping.

Encoder dropout is authored on the HyperParameters-owned surface, handed off through `LanguageModelConfig`, sliced through `EncoderLayerConstructionHP`, and passed to FFN construction through `FeedForwardLayerConstructionHP`. Do not add layer-local dropout defaults or copy `dropout_rate` through ad-hoc config structs.

Config value logging is owned by `training/Phases/ConfigDump.{hpp,cu}`. Phase/startup modules may log lifecycle/status messages, but they MUST NOT print per-field config values (for example architecture dimensions, logging/tape knobs, telemetry lattice dimensions, or feature gate values) outside `ConfigDump`. If a value is useful in startup logs, add it to `ConfigDump` instead of emitting it at the consumer site.

## Fail-loud defaults (Rule 20)
Algorithmic config fields MUST default to `0` and throw if not loaded. Hardcoded defaults like `int max_seq_len = 512;` are forbidden — they hide silent fallbacks.

```cpp
int max_seq_len = 0;  // ✅
// ...load from JSON...
if (max_seq_len == 0)
    throw std::runtime_error("max_seq_len missing from ai_config.json");
```

`training.config.sliding_window_stride` is an authored field, not a derived fallback. It must be set explicitly in `ai_config.json`, must be `> 0`, and must be `<=` the effective startup `max_seq_len` after stability overrides. If you want the old 12.5% overlap behavior for `max_seq_len=1024`, set `sliding_window_stride` to `896`.

## Validation token budget
Validation MUST use Phase1-authored config facts (`ctx.config.max_seq_len`, `ctx.config.hyperparameters.batch_size`, `ctx.model_allocation.model_max_tokens_per_batch`, or a non-duplicate explicit `HyperparameterGroupings.hpp` view such as `trainingFixedShapeHP()`), never the `LanguageModel` config accessor and never a hardcoded constant — buffer overflow crash otherwise. Batch scheduling consumes configured `max_seq_len` and `batch_size` directly; it must not derive sequence length from `max_tokens_per_batch` or a capacity wrapper.
