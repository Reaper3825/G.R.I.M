# Three-Phase Training Architecture

Training entry point: `train_gpu.cu` → `loadAiConfigSnapshot()` → `finalizeLanguageModelConfig(snapshot.document, ..., TRAINING)` → `executePhase1(startup_config)` → `executePhase2()` → `executePhase3()`. Inference runtime entry point: `train_gpu.cu --inference` → `loadAiConfigSnapshot()` → `finalizeLanguageModelConfig(snapshot.document, ..., INFERENCE)` → `executePhase1(startup_config)` → trainer-owned Phase 2 inference worker → `executePhase2TextInference(...)` over the Phase1-authored `TrainingContext`. Data flows through explicit phase handoffs inside the trainer process; HTTP/front-end code does not own or borrow `TrainingContext`.

Inference/control entry point: `grim_text_server.cpp` is only the user-facing HTTP bridge. It launches `train_gpu --inference --inference-worker-port <port>`, waits for the trainer-owned worker readiness endpoint, and forwards `/api/generate` / `/api/chat` request JSON. It must not include `Phase1_Startup.hpp`, call `executePhase1()`, load config, store `TrainingContext`, touch tokenizer artifacts, construct `BatchPayload`, derive `GenerationHP`, decode tokens, or link CUDA/model/training objects. The trainer process is the highest-level runtime orchestrator and is the only process that owns training-vs-inference mode selection and durable runtime state.

`Phase1_Startup` is the shared durable bootstrap boundary for both training and inference: validated root config, CUDA device/stream/cuBLAS/PBM setup, tokenizer artifact loading, model/layer allocation, checkpoint materialization, parameter registration, and runtime workspace allocation are authored before any graph execution. Training then enters `Phase2_TrainingLoop`; inference enters sibling `Phase2_InferenceLoop` rather than hiding inference behavior inside shared forward or autograd files.

| Phase | File | Responsibility |
|-------|------|----------------|
| 1 — Startup | `training/Phases/Phase1_Startup.cu` | Config, tokenizer, data loading, model init, optimizer setup |
| 2 — Training Loop | `training/Phases/Phase2_TrainingLoop.cu` | Batching, forward/backward, gradient clipping, epoch metrics, checkpointing |
| 2 — Inference Loop | `training/Phases/Phase2_InferenceLoop.*` | Trainer-owned text/payload inference orchestration over the same startup-authored model/runtime |
| 3 — Cleanup | `training/Phases/Phase3_Cleanup.cu` | Final checkpoint, summary, resource release |

**Edit the phase file**, never `train_gpu.cu`, when modifying training logic.

Static hyperparameter groupings are explicit boundary payloads, not extra owners on `TrainingContext`. Payload types and slicers live in `HyperparameterGroupings.hpp`; validation lives earlier in `HyperParameters_GPU.hpp` root document validators before those payloads are sliced. Phase 2 derives `LossConfigHP` only at the immediate autograd call boundary that needs it. `AutogradContext` must not store it. Do not add `initialized` sentinels, `TrainingLoopState` wrappers, or a second `TrainingContext` loss-config owner.

Tokenizer artifact preparation is still Phase 1 startup work, not a separate tokenizer pre-phase owned by `train_gpu.cu`. The training order is `train_gpu.cu` loads `AiConfigSnapshot::document`, finalizes it through HyperParameters, then `executePhase1(startup_config)` stores the transitional finalized handoff on `TrainingContext.config` → `LoggingReady()` → `MemorySnapshotReady()` → `HyperparametersReady()` → tokenizer subprocess (`train_tokenizer`, vocab + GRMT preparation) → `LoadTrainingData()`. The inference order uses the same `executePhase1(startup_config)` boundary with `ModelExecutionMode::INFERENCE`, then `LoadInferenceTokenizer()` loads the artifact bundle and `ModelAllocated()` initializes inference runtime workspaces before `CheckpointLoaded()`. `LoggingReady()` must consume an already-authored `TrainingContext.config`, and `executePhase1()` must not hide or repeat config loading. Token layout is canonical in `TokenLayout.hpp`; startup must not mutate or "reconfigure" it. This keeps tokenizer/runtime setup behind the same validated startup config root that model startup uses. Fixed training shape is no longer stored as a Phase1 sidecar; startup/model/payload/diagnostic code re-slices the HyperParameters-validated rectangle from `HyperparameterGroupings.hpp::trainingFixedShapeHP()` when it needs the grouped view. If `training.config.subprocess_tokenizer_only_mode=true`, `executePhase1()` returns `Phase1Outcome::tokenizer_only_complete` and the orchestrator exits cleanly without entering Phases 2-3.

Batch schedule ownership is single-pass: `PlannedBatchesReady()` is the only Phase 1 startup step that calls `buildEpochBatches()` for training. `EpochPlanReady()` must derive `total_batches` from the authored `train_payloads` count, not from a scheduler dry-run/preflight wrapper. This prevents duplicated batch-policy execution and keeps Phase 2 consuming only Phase1-authored payloads/order. `BatchAssignment` is an ID/order handoff only; it must not carry min/max/current-token geometry or overflow state. The scheduler must emit exactly `batch_size` sequence IDs per batch — no partial dynamic batch, no overflow batch, no length curriculum/prefer-short-first policy, and no average batch-size telemetry. If the post-filtered sequence count leaves an incomplete tail, `buildBatches()` discards those trailing rows rather than emitting a partial batch; training may apply a seeded shuffle before fixed-size chunking and a seeded fixed-batch shuffle after chunking, while validation preserves source order. `Batching_GPU.cu::buildBatches()` consumes configured `StartupConfig.max_seq_len` and `TrainingHyperparameters.batch_size` directly; it must not derive sequence length from `max_tokens_per_batch` or from a mirrored capacity struct/grouping, and `BatchSchedule` must not persist a copied `sequence_cap` field. Any fixed-rectangle token totals logged from `BatchSchedule` are projections only; concrete padded geometry (`max_seq_len`, `total_tokens`, `padding_tokens`) is authored later by `BatchPayload`, which reads the selected post-sliding-window rows and pads every row to the configured sequence cap.

`GRMTDataLoader` owns only raw `.grmt` row deserialization into `TrainingSequence` objects. It must not expose stable `seq_id` sample accessors or long-lived row views, because Phase 1 still has to split train/val data, inject boundaries, apply sliding windows, and filter invalid rows. `LoadTrainingData()` passes `TokenizerHP` and `DataLoadingHP` into this startup data path and reads `StartupConfig.max_seq_len` directly for the fixed sliding-window cap; do not add local wrapper structs or capacity groupings that mirror those config fields. Phase 1 startup logging should surface this path explicitly: emit GRMT header/read progress through the active `TrainingLogger`, then log split/window/view milestones in `TrainingData.cu` so large corpus startups are observable in `training_<session>.log`. Training `seq_ids` are authored only after `applySlidingWindows()` when `TrainingData.cu` builds `train_views` / `val_views`; `Batching_GPU.cu` schedules those post-window view indices, and `BatchPayload.cu` consumes them.

`.grmt` header ownership is centralized in `Shared/GRMT/GrmtFormat.hpp`: the magic value, four-field header layout, current-version check, nonzero sequence/vocab guards, and header writes live there. Startup/data tools may read the header only through that boundary; after it returns a validated header, callers continue with their own stream-specific payload work.

Startup model tensor registration lives in `training/Phases/Startup/Model/ParameterGroupRegistration.{hpp,cu}`. `Startup/Model/ParameterRegistry.hpp::StartupParameterRegistry` is the single durable owner for the `ParameterGroup` vector and migrated FFN/selector/MTP writable parameter bundles; `LanguageModel` and `TrainingContext` must not mirror that inventory. FFN tensors are allocated and Xavier-initialized by the ParameterGroupRegistration startup module into per-layer registry bundles; shared forward builds per-call `FeedForwardParameterViews` directly from `ModelForwardRequest::parameter_registry`, and `FeedForwardLayer` stores HP only instead of owning or borrowing trainable tensors. The startup module receives the explicit Phase1 `AiConfigSnapshot`, `GpuModelState`, and `StartupParameterRegistry`, discovers trainable tensors, records non-owning `ParameterGroup` metadata through the registry-owned vector, stamps each group from the finalized config precision fields, and binds optimizer moment tensors owned by `OptimizerState`. Registration must not receive a parallel config/policy owner beside the config it already consumes.

`Startup/Model/ParameterGroupRegistration::buildParameterGroups(config, gpu_model_state, parameter_registry)` is transaction-safe: registration rebuilds a local vector, performs all configured trainable-tensor validation there, and swaps it into `StartupParameterRegistry::parameter_groups` only after success. A thrown registration check must never leave the registry with a half-rebuilt parameter inventory.

The **Optimizer Window** is the only Phase 2 boundary where a completed accumulation window becomes updated weights. `runEpoch()` owns the chronological split: it authors `BatchAutogradPlan` with the active `batch_idx` and accumulation facts, calls `processBatch()` for exactly one microbatch forward/loss/backward pass, advances the accumulation slot after the batch returns, and opens the optimizer window only when the accumulation window is full. At that boundary, Phase2 normalizes the registered parameter gradients once for the full accumulation window, then runs clipping/diagnostics/update. `processBatch()` must not read or mutate `OptimizerContext` and must not call `launchOptimizerUpdate()`. Startup-owned forward topology lives on `training/Phases/Startup/Model/ModelGpuState.hpp`; when Phase2 needs encoder/embedding/LM-head/ScratchBlock/ExecutionBlock pointers, it should request the read view from `TrainingContext::gpu_model` there instead of minting a Phase2-local topology wrapper or routing those checks through `LanguageModel`. Configured optimizer stepping lives in `Shared/Optimizers/OptimizerUpdate_GPU.{hpp,cu}` behind `launchOptimizerUpdate()`. Phase 2 must not branch on `optimizer_kind` or hand-wire AdamW/RAdamW launch arguments; the epoch-owned optimizer window passes the grouped `OptimizerUpdateHP`, learning rate, optimizer step, stream, and registered parameter groups after the accumulation window is full. AdamW/RAdamW-specific kernel launches and embedding-freeze skip semantics belong to the optimizer dispatcher, while each concrete optimizer file owns only its own kernel/step implementation. See [Optimizer.md](Optimizer.md) for the full boundary policy.

Startup model allocation lives in `training/Phases/Startup/Model/ModelAllocationState.{hpp,cu}` plus `training/Phases/Startup/Model/ModelGpuAssembly.{hpp,cu}`. Phase 1 owns the model startup order through model/runtime readiness only: CUDA device context, `LanguageModel` construction, stream controller, cuBLAS, PBM, GPU model assembly, parameter registration/verification, and `TrainingState` allocation. The startup bootstrap free-function API is declared in `ModelGpuAssembly.hpp`, while the durable GPU model assembly implementation stays in `ModelGpuAssembly.cu`; `ModelAllocationState` remains the only caller that sequences them. Durable encoder/layer topology is owned on `TrainingContext::gpu_model` (`Startup::GpuModelState`), while migrated FFN/selector/MTP writable parameter bundles are owned on `TrainingContext::parameter_registry`. `LanguageModel` only borrows those startup-owned structures for compatibility while the older model-centric boundary is being removed. Startup, Phase2, and serialization code that already has `TrainingContext` should read FFN/MTP/selector state from `parameter_registry` and encoder/layer topology from `gpu_model` instead of routing through `GpuModelState` or adding new `LanguageModel` wrappers. `grim_language_model_cuda.hpp` must not advertise Phase 1 startup entry points. Checkpoint weight materialization is the next explicit Phase 1 op, `CheckpointLoaded(ctx)`, implemented in `training/Phases/Startup/CheckpointLoad.{hpp,cu}`. The high-level Phase 1 list must keep checkpoint load as a single op line after `ModelAllocated(ctx)` and before `ResumeStateReady(ctx)` so optimizer sidecar resume reads the already-selected `ctx.loaded_checkpoint_path`. Checkpoint selection is no longer a directory scan or an "older checkpoint" fallback: `CheckpointLoaded(ctx)` slices `CheckpointLoadHP` from `HyperparameterGroupings.hpp::checkpointLoadHP(config, requested_path, execution_mode)` and obeys only that explicit request. If the requested checkpoint is unusable, inference must fail loud; training starts fresh.

Durable GPU layer assembly lives in `training/Phases/Startup/Model/ModelGpuAssembly.cu` as the startup free function `GRIMText::Training::Startup::assembleGpuModel(config, training_state, gpu_model_state, parameter_registry, weight_init_seed)`. This Startup/Model source populates the startup-owned `GpuModelState` with the GPU encoder, PBM owner, `EmbeddingLayer`, LM head, ScratchBlock, and optional execution block, while `parameter_registry` owns the optional decode-time selector and MTP parameter bundles. It must not allocate `TrainingState` activation caches, optimizer state, parameter groups, checkpoints, forward/backward paths, or Phase 2 loop state. Checkpoint serialization now reads/writes token embeddings only through the durable `EmbeddingLayer` device tensor; there is no parallel CPU embedding owner on `LanguageModel`.

Selector/MTP writable parameter access and checkpoint I/O are no longer `LanguageModel` member boundaries: callers with `TrainingContext` must go directly through `TrainingContext::parameter_registry`, and checkpoint save/load must use `Common/grim_model_serialization.{hpp,cu}` free functions with explicit `LanguageModel`, `GpuModelState`, and `StartupParameterRegistry` inputs.

Shared forward boundary: `Shared/Forward/ModelForward_GPU.hpp` receives a caller-authored `ModelForwardGraphPolicy`, not a training/inference mode. Phase2 training asks for an autograd-connected retained graph with dropout; Phase2 inference owns the autoregressive generation session and explicitly rebuilds `ModelForwardRequest` / `ModelForwardRuntimePayload` in `training/Phases/Phase2_InferenceLoop.cu` for read-only full-context scoring with detached parameter views and no dropout. `ModelForwardRequest::parameter_registry` is the explicit durable parameter source for registry-migrated bundles such as FFN; forward builds detached or connected per-call views there instead of asking compute layers for cached borrowed parameters. `Forward` must remain a read-only graph primitive over durable model state; only orchestration decides whether the call participates in training or inference.

Inference result payloads such as `GeneratedSequence` belong next to the forward/inference boundary under `Shared/Forward/`, not on `grim_language_model_cuda.hpp`. They are Phase2 inference payload types, not durable model topology.

The model-stats payload and free-function API live in `Common/ModelStats.hpp`, and `computeModelStats(const StartupParameterRegistry&)` lives in `Common/ModelStats.cu`. The implementation reads the registry-owned parameter-group inventory after startup registration and must classify counts from explicit `ParamStatsBucket` metadata written by `ParameterGroupRegistration`. It must not estimate parameter counts from config formulas, compare raw tensor pointers, or re-slice hyperparameters.
