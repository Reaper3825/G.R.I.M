# Three-Phase Training Architecture

Entry point: `train_gpu.cu` → `executePhase1()` → `executePhase2()` → `executePhase3()`. Data flows via the `TrainingContext` struct (no globals).

| Phase | File | Responsibility |
|-------|------|----------------|
| 1 — Startup | `training/Phases/Phase1_Startup.cu` | Config, tokenizer, data loading, model init, optimizer setup |
| 2 — Training Loop | `training/Phases/Phase2_TrainingLoop.cu` | Batching, forward/backward, gradient clipping, epoch metrics, checkpointing |
| 3 — Cleanup | `training/Phases/Phase3_Cleanup.cu` | Final checkpoint, summary, resource release |

**Edit the phase file**, never `train_gpu.cu`, when modifying training logic.

Static hyperparameter groupings are explicit boundary payloads, not extra owners on `TrainingContext`. For loss, startup code validates the grouping with `lossConfigHP()` against the authoritative `TrainingContext.config.hyperparameters`, and Phase 2 derives `LossConfigHP` only at the immediate autograd call boundary that needs it. `AutogradContext` must not store it. Do not add `initialized` sentinels, `TrainingLoopState` wrappers, or a second `TrainingContext` loss-config owner.

Tokenizer artifact preparation is Phase 1 startup work, not a pre-phase owned by `train_gpu.cu`. The order is `loadStartupConfig()` in `executePhase1()` → `LoggingReady()` → `MemorySnapshotReady()` → `HyperparametersReady()` → tokenizer subprocess (`train_tokenizer`, vocab + GRMT preparation) → `LoadTrainingData()`. `LoggingReady()` must consume an already-authored `TrainingContext.config`; it is not allowed to hide config loading. Token layout is canonical in `TokenLayout.hpp`; startup must not mutate or "reconfigure" it. This keeps the tokenizer run behind the same validated `StartupConfig` / `TrainingHyperparameters` path that model startup uses, while still running before `LoadTrainingData()` consumes the generated vocab and training-data files. Fixed training shape is no longer stored as a Phase1 sidecar; startup/model/payload/diagnostic code re-derives the checked rectangle from `HyperparameterGroupings.hpp::trainingFixedShapeHP()` when it needs the grouped view. If `subprocess.tokenizer.only_mode=true`, `executePhase1()` returns `Phase1Outcome::tokenizer_only_complete` and the orchestrator exits cleanly without entering Phases 2-3.

Batch schedule ownership is single-pass: `PlannedBatchesReady()` is the only Phase 1 startup step that calls `buildEpochBatches()` for training. `EpochPlanReady()` must derive `total_batches` from the authored `train_payloads` count, not from a scheduler dry-run/preflight wrapper. This prevents duplicated batch-policy execution and keeps Phase 2 consuming only Phase1-authored payloads/order. `BatchAssignment` is an ID/order handoff only; it must not carry min/max/current-token geometry or overflow state. The scheduler must emit exactly `batch_size` sequence IDs per batch — no partial dynamic batch, no overflow batch, no length curriculum/prefer-short-first policy, and no average batch-size telemetry. If the post-filtered sequence count leaves an incomplete tail, `buildBatches()` discards those trailing rows rather than emitting a partial batch; training may apply a seeded shuffle before fixed-size chunking and a seeded fixed-batch shuffle after chunking, while validation preserves source order. `Batching_GPU.cu::buildBatches()` consumes configured `StartupConfig.max_seq_len` and `TrainingHyperparameters.batch_size` directly; it must not derive sequence length from `max_tokens_per_batch` or from a mirrored capacity struct/grouping, and `BatchSchedule` must not persist a copied `sequence_cap` field. Any fixed-rectangle token totals logged from `BatchSchedule` are projections only; concrete padded geometry (`max_seq_len`, `total_tokens`, `padding_tokens`) is authored later by `BatchPayload`, which reads the selected post-sliding-window rows and pads every row to the configured sequence cap.

`GRMTDataLoader` owns only raw `.grmt` row deserialization into `TrainingSequence` objects. It must not expose stable `seq_id` sample accessors or long-lived row views, because Phase 1 still has to split train/val data, inject boundaries, apply sliding windows, and filter invalid rows. `LoadTrainingData()` passes `TokenizerHP` and `DataLoadingHP` into this startup data path and reads `StartupConfig.max_seq_len` directly for the fixed sliding-window cap; do not add local wrapper structs or capacity groupings that mirror those config fields. Phase 1 startup logging should surface this path explicitly: emit GRMT header/read progress through the active `TrainingLogger`, then log split/window/view milestones in `TrainingData.cu` so large corpus startups are observable in `training_<session>.log`. Training `seq_ids` are authored only after `applySlidingWindows()` when `TrainingData.cu` builds `train_views` / `val_views`; `Batching_GPU.cu` schedules those post-window view indices, and `BatchPayload.cu` consumes them.

`.grmt` header ownership is centralized in `Shared/GRMT/GrmtFormat.hpp`: the magic value, four-field header layout, current-version check, nonzero sequence/vocab guards, and header writes live there. Startup/data tools may read the header only through that boundary; after it returns a validated header, callers continue with their own stream-specific payload work.

Startup model tensor registration lives in `training/Phases/Startup/Model/ParameterGroupRegistration.{hpp,cu}`. `LanguageModel` still owns the durable `parameter_groups_` vector and parameter tensors; the startup module only discovers trainable tensors, records non-owning `ParameterGroup` metadata, stamps each group from the model's actual `LanguageModelConfig` precision fields, and binds optimizer moment tensors owned by `OptimizerState`. Registration must not receive a separate sidecar config/policy object beside the model/config it already consumes.

`Startup/Model/ParameterGroupRegistration::buildParameterGroups(model)` is transaction-safe: registration rebuilds a local vector, performs all configured trainable-tensor validation there, and swaps it into `LanguageModel::parameter_groups_` only after success. A thrown registration check must never leave `LanguageModel` with a half-rebuilt parameter inventory.

The **Optimizer Window** is the only Phase 2 boundary where a completed accumulation window becomes updated weights. `runEpoch()` owns the chronological split: it authors `BatchAutogradPlan` with the active `batch_idx` and accumulation facts, calls `processBatch()` for exactly one microbatch forward/loss/backward pass, advances the accumulation slot after the batch returns, and opens the optimizer window only when the accumulation window is full. At that boundary, Phase2 normalizes the registered parameter gradients once for the full accumulation window, then runs clipping/diagnostics/update. `processBatch()` must not read or mutate `OptimizerContext` and must not call `launchOptimizerUpdate()`. Configured optimizer stepping lives in `Shared/Optimizers/OptimizerUpdate_GPU.{hpp,cu}` behind `launchOptimizerUpdate()`. Phase 2 must not branch on `optimizer_kind` or hand-wire AdamW/RAdamW launch arguments; the epoch-owned optimizer window passes the grouped `OptimizerUpdateHP`, learning rate, optimizer step, stream, and registered parameter groups after the accumulation window is full. AdamW/RAdamW-specific kernel launches and embedding-freeze skip semantics belong to the optimizer dispatcher, while each concrete optimizer file owns only its own kernel/step implementation. See [Optimizer.md](Optimizer.md) for the full boundary policy.

Startup model allocation lives in `training/Phases/Startup/Model/ModelAllocationState.{hpp,cu}`. It owns the Phase 1 model startup order: CUDA device context, `LanguageModel` construction, stream controller, cuBLAS, PBM, GPU model assembly, parameter registration/verification, `TrainingState` allocation, and checkpoint load/resume.

Durable GPU layer assembly lives in `training/Phases/Startup/Model/ModelGpuAssembly.cu` as `LanguageModel::initGPU(weight_init_seed)`. This Startup/Model source creates the GPU encoder, embedding layer, LM head, ScratchBlock, and optional reasoning/execution/decode-time/MTP heads. It must not allocate `TrainingState` activation caches, optimizer state, parameter groups, checkpoints, forward/backward paths, or Phase 2 loop state.

`LanguageModel::getModelStats()` lives in `Common/ModelStats.cu`. It reads the model-owned `parameter_groups_` inventory after startup registration and must classify counts from explicit `ParamStatsBucket` metadata written by `ParameterGroupRegistration`. It must not estimate parameter counts from config formulas, compare raw tensor pointers, or re-slice hyperparameters.
