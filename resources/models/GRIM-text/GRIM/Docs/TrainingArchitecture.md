# Three-Phase Training Architecture

Training entry point: `train_gpu.cu` → `loadAiConfigSnapshot()` → `finalizeLanguageModelConfig(snapshot.document, ..., TRAINING)` → `executePhase1(startup_config)` → `executePhase2()` → `executePhase3()`. Inference runtime entry point: `train_gpu.cu --inference` → `loadAiConfigSnapshot()` → `finalizeLanguageModelConfig(snapshot.document, ..., INFERENCE)` → `executePhase1(startup_config)` → trainer-owned Phase 2 inference worker → `executePhase2TextInference(ctx, tokenizer, ...)` over the Phase1-authored `TrainingContext` plus an explicit inference tokenizer owner. Data flows through explicit phase handoffs inside the trainer process; HTTP/front-end code does not own or borrow `TrainingContext`.

Inference/control entry point: `grim_text_server.cpp` is only the user-facing HTTP bridge. It launches `train_gpu --inference --inference-worker-port <port>`, waits for the trainer-owned worker readiness endpoint, and forwards `/api/generate` / `/api/chat` request JSON. It must not include `Phase1_Startup.hpp`, call `executePhase1()`, load config, store `TrainingContext`, touch tokenizer artifacts, construct `BatchPayload`, derive `GenerationHP`, decode tokens, or link CUDA/model/training objects. The trainer process is the highest-level runtime orchestrator and is the only process that owns training-vs-inference mode selection and durable runtime state.

`Phase1_Startup` is the shared durable bootstrap boundary for both training and inference: validated root config, CUDA device/stream/cuBLAS/PBM setup, model/layer allocation, checkpoint materialization, parameter registration, and runtime workspace allocation are authored before any graph execution. Training carries only GRMT-authored vocab facts on `SequenceData.vocab_size`, syncs `TrainingContext.config.vocab_size` from that fact during startup, and code that needs token ranges derives `TokenLayout` locally from `TokenLayout.hpp` instead of storing a second layout owner on `TrainingContext`. Training/inference diagnostics that already have a batch in scope must read `BatchPayload::vocab_size` instead of a startup sidecar. Inference additionally loads a runtime tokenizer and hands that explicit owner to Phase 2 inference instead of storing it on `TrainingContext`. Training then enters `Phase2_TrainingLoop`; inference enters sibling `Phase2_InferenceLoop` rather than hiding inference behavior inside shared forward or autograd files.

| Phase | File | Responsibility |
|-------|------|----------------|
| 1 — Startup | `training/Phases/Phase1_Startup.cu` | Config, token layout/data loading, model init, optimizer setup, explicit inference tokenizer handoff |
| 2 — Training Loop | `training/Phases/Phase2_TrainingLoop.cu` | Batching, forward/backward, gradient clipping, epoch metrics, checkpointing |
| 2 — Inference Loop | `training/Phases/Phase2_InferenceLoop.*` | Trainer-owned text/payload inference orchestration over the same startup-authored model/runtime |
| 3 — Cleanup | `training/Phases/Phase3_Cleanup.cu` | Final checkpoint, summary, resource release |

**Edit the phase file**, never `train_gpu.cu`, when modifying training logic.

Static hyperparameter groupings are explicit boundary payloads, not extra owners on `TrainingContext`. Payload types and slicers live in `HyperparameterGroupings.hpp`; validation lives earlier in `HyperParameters_GPU.hpp` root document validators before those payloads are sliced. Phase 2 derives `LossConfigHP` only at the immediate autograd call boundary that needs it. `AutogradContext` must not store it. Do not add `initialized` sentinels, `TrainingLoopState` wrappers, or a second `TrainingContext` loss-config owner.

Tokenizer artifact preparation is still Phase 1 startup work, not a separate tokenizer pre-phase owned by `train_gpu.cu`. The training order is `train_gpu.cu` loads `AiConfigSnapshot::document`, finalizes it through HyperParameters, then `executePhase1(startup_config)` stores the transitional finalized handoff on `TrainingContext.config` → `LoggingReady()` → local `captureMemorySnapshotOrThrow()` evidence for the startup config dump → `HyperparametersReady()` → tokenizer subprocess (`train_tokenizer`, vocab + GRMT preparation) → `LoadTrainingData()`. `LoadTrainingData()` reads the final vocab size from the `.grmt` header into `ctx.data.vocab_size` and syncs `ctx.config.vocab_size`; the startup memory snapshot is passed in as a plain value for logging only and is not stored on `TrainingContext`. Downstream batching/diagnostics derive `TokenLayout` locally from that authoritative vocab size via `TokenLayout.hpp`, and must not instantiate a runtime tokenizer just to ask for type counts. The inference order uses the same `executePhase1(startup_config)` boundary with `ModelExecutionMode::INFERENCE`, then `LoadInferenceTokenizer(config, logger)` loads the artifact bundle, syncs `config.vocab_size` from `tokenizer->vocabSize()`, and returns the runtime tokenizer as an explicit Phase1 result owner consumed by `train_gpu`'s inference worker. `LoggingReady()` must consume an already-authored `TrainingContext.config`, and `executePhase1()` must not hide or repeat config loading. Token layout is canonical in `TokenLayout.hpp`; startup must not mutate or "reconfigure" it. If `training.config.subprocess_tokenizer_only_mode=true`, `executePhase1()` returns `Phase1Outcome::tokenizer_only_complete` and the orchestrator exits cleanly without entering Phases 2-3.

Batch schedule ownership is single-pass: `PlannedBatchesReady()` is the only Phase 1 startup step that calls `buildEpochBatches()` for training. `EpochPlanReady()` must derive `total_batches` from the authored `train_payloads` count, not from a scheduler dry-run/preflight wrapper. This prevents duplicated batch-policy execution and keeps Phase 2 consuming only Phase1-authored payloads/order. `BatchAssignment` is an ID/order handoff only; it must not carry min/max/current-token geometry or overflow state. The scheduler must emit exactly `batch_size` sequence IDs per batch — no partial dynamic batch, no overflow batch, no length curriculum/prefer-short-first policy, and no average batch-size telemetry. If the post-filtered sequence count leaves an incomplete tail, `buildBatches()` discards those trailing rows rather than emitting a partial batch; training may apply a seeded shuffle before fixed-size chunking and a seeded fixed-batch shuffle after chunking, while validation preserves source order. `Batching_GPU.cu::buildBatches()` consumes configured `StartupConfig.max_seq_len` and `TrainingHyperparameters.batch_size` directly; it must not derive sequence length from `max_tokens_per_batch` or from a mirrored capacity struct/grouping, and `BatchSchedule` must not persist a copied `sequence_cap` field. Any fixed-rectangle token totals logged from `BatchSchedule` are projections only; concrete padded geometry (`max_seq_len`, `total_tokens`, `padding_tokens`) is authored later by `BatchPayload`, which reads the selected post-sliding-window rows and pads every row to the configured sequence cap.

`Shared/DataLoader/DataLoader.cu` owns Phase 1's raw `.grmt` startup load boundary as private free functions over `GrmtCorpusReader`: progress-aware row deserialization, side-channel sanitation, atom diagnostics, and fail-loud NumberEncoder compatibility validation against the finalized `number_encoder_*` config return canonical `GrmtSequence` rows plus the header vocab size. It must not expose stable `seq_id` sample accessors, long-lived row views, or a stateful loader class, because Phase 1 still has to split train/val data, inject boundaries, apply sliding windows, and filter invalid rows. `LoadTrainingData()` passes `TokenizerHP`, `DataLoadingHP`, and the finalized `NumberEncoderConstructionHP` view into this startup data path and reads `StartupConfig.max_seq_len` directly for the fixed sliding-window cap; do not add local wrapper structs or capacity groupings that mirror those config fields. Phase 1 startup logging should surface this path explicitly: emit GRMT header/read progress through the active `TrainingLogger`, then log split/window/view milestones in `Shared/DataLoader/DataLoader.cu` so large corpus startups are observable in `training_<session>.log`. Training `seq_ids` are authored only after `applySlidingWindows()` when `Shared/DataLoader/DataLoader.cu` builds `train_views` / `val_views`; `Batching_GPU.cu` schedules those post-window view indices, and `BatchPayload.cu` consumes them.

`.grmt` header ownership is centralized in `Shared/GRMT/GrmtFormat.hpp`: the magic value, four-field header layout, current-version check, nonzero sequence/vocab guards, and header writes live there. Startup/data tools may read the header only through that boundary; after it returns a validated header, callers continue with their own stream-specific payload work.

Startup model tensor registration lives in `training/Phases/Startup/Model/ParameterGroupRegistration.{hpp,cu}`. `Startup/Model/ParameterRegistry.hpp::StartupParameterRegistry` is the single durable owner for the `ParameterGroup` vector and migrated FFN/execution-block/selector writable parameter bundles; `LanguageModel` and `TrainingContext` must not mirror that inventory. FFN tensors are allocated and Xavier-initialized by the ParameterGroupRegistration startup module into per-layer registry bundles; execution-block tensors are allocated and initialized there into `StartupParameterRegistry::execution_block_parameters`; shared forward builds per-call parameter views directly from `ModelForwardRequest::parameter_registry`, and compute layers store HP/runtime scratch only instead of owning or borrowing trainable tensors. The startup module receives the explicit Phase1 `AiConfigSnapshot`, `GpuModelState`, and `StartupParameterRegistry`, discovers trainable tensors, records non-owning `ParameterGroup` metadata through the registry-owned vector, stamps each group from the finalized config precision fields, and binds optimizer moment tensors owned by `OptimizerState`. Registration must not receive a parallel config/policy owner beside the config it already consumes.

`Startup/Model/ParameterGroupRegistration::buildParameterGroups(config, gpu_model_state, parameter_registry)` is transaction-safe: registration rebuilds a local vector, performs all configured trainable-tensor validation there, and swaps it into `StartupParameterRegistry::parameter_groups` only after success. A thrown registration check must never leave the registry with a half-rebuilt parameter inventory.

The **Optimizer Window** is the only Phase 2 boundary where a completed accumulation window becomes updated weights. `runEpoch()` owns the chronological split: it authors `BatchAutogradPlan` with the active `batch_idx` and accumulation facts, calls `processBatch()` for exactly one microbatch forward/loss/backward pass, advances the accumulation slot after the batch returns, and opens the optimizer window only when the accumulation window is full. At that boundary, Phase2 normalizes the registered parameter gradients once for the full accumulation window, then runs clipping/diagnostics/update. `processBatch()` must not read or mutate `OptimizerContext` and must not call `launchOptimizerUpdate()`. Startup-owned forward topology lives on `training/Phases/Startup/Model/ModelGpuState.hpp`; when Phase2 needs startup-owned forward facts such as the GPU encoder, ScratchBlock pointer, or execution-block enablement bit, it should request the read view from `TrainingContext::gpu_model` there instead of minting a Phase2-local topology wrapper or routing those checks through `LanguageModel`. Configured optimizer stepping lives in `Shared/Optimizers/OptimizerUpdate_GPU.{hpp,cu}` behind `launchOptimizerUpdate()`. Phase 2 must not branch on `optimizer_kind` or hand-wire AdamW/RAdamW launch arguments; the epoch-owned optimizer window passes the grouped `OptimizerUpdateHP`, learning rate, optimizer step, stream, and registered parameter groups after the accumulation window is full. AdamW/RAdamW-specific kernel launches and embedding-freeze skip semantics belong to the optimizer dispatcher, while each concrete optimizer file owns only its own kernel/step implementation. See [Optimizer.md](Optimizer.md) for the full boundary policy.

Startup model allocation lives in `training/Phases/Startup/Model/ModelAllocationState.{hpp,cu}` plus `training/Phases/Startup/Model/ModelGpuAssembly.{hpp,cu}`. Phase 1 owns the model startup order through model/runtime readiness only: CUDA device context, `LanguageModel` construction, stream controller, cuBLAS, PBM, GPU model assembly, parameter registration/verification, and `TrainingState` allocation. The startup bootstrap free-function API is declared in `ModelGpuAssembly.hpp`, while the durable GPU model assembly implementation stays in `ModelGpuAssembly.cu`; `ModelAllocationState` remains the only caller that sequences them. Durable encoder/layer topology is owned on `TrainingContext::gpu_model` (`Startup::GpuModelState`), while migrated FFN/selector writable parameter bundles are owned on `TrainingContext::parameter_registry`. `LanguageModel` only borrows those startup-owned structures for compatibility while the older model-centric boundary is being removed. Startup, Phase2, and serialization code that already has `TrainingContext` should read FFN/selector state from `parameter_registry` and encoder/layer topology from `gpu_model` instead of routing through `GpuModelState` or adding new `LanguageModel` wrappers. `grim_language_model_cuda.hpp` must not advertise Phase 1 startup entry points. `CheckpointPlanReady(ctx)` resolves the parameter source before training-data and model initialization. The typed `training_stage` checkpoint grouping controls whether startup may choose fresh parameters: PT may initialize fresh when no checkpoint was requested or when `latest` discovery finds none, while SFT, DPO, RLHF, inference, and explicitly named checkpoint requests require a usable checkpoint. Fresh-only corpus initialization is legal only for `FRESH_INITIALIZATION`; a planned checkpoint restore skips it. Model buffers are still allocated before materialization so the loader has destinations. `CheckpointLoaded(ctx)` then materializes the already-planned checkpoint after `ModelAllocated(ctx)` and before `ResumeStateReady(ctx)`. A planned restore must load one of its preflight-validated candidates or fail loudly; it never falls back to fresh model parameters.

Durable GPU layer assembly lives in `training/Phases/Startup/Model/ModelGpuAssembly.cu` as the startup free function `GRIMText::Training::Startup::assembleGpuModel(config, training_state, gpu_model_state, parameter_registry, weight_init_seed)`. This Startup/Model source assembles the startup-owned GPU encoder / ScratchBlock topology and the compatibility-owned embedding / LM-head pieces, while `parameter_registry` owns the execution-block parameter bundle plus the optional decode-time selector parameter bundle. `ExecutionBlockLayer` is deleted: execution-block behavior now hangs off registry-owned tensors, explicit HP payloads, and runtime-owned diagnostics/workspace on shared forward. Startup assembly must not allocate `TrainingState` activation caches, optimizer state, parameter groups, checkpoints, forward/backward paths, or Phase 2 loop state. Checkpoint serialization now reads/writes token embeddings only through the durable `EmbeddingLayer` device tensor; there is no parallel CPU embedding owner on `LanguageModel`.

Selector writable parameter access and checkpoint I/O are no longer `LanguageModel` member boundaries: callers with `TrainingContext` go directly through `TrainingContext::parameter_registry`. `Common/ParameterCheckpoint.{hpp,cu}` owns strict `.grimckpt` save/load. Phase 3 and startup pass the finalized `AiConfigSnapshot`, `StartupParameterRegistry`, and primary CUDA stream into that boundary; the implementation iterates the registry in its authored order for both device-to-host save and host-to-device restore. The registry is the complete tensor inventory, while the config contributes only parameterless semantic compatibility facts. The former architecture-specific serializer and TransformerModel schema have no compatibility path.

Shared forward boundary: `Shared/Forward/ModelForward_GPU.hpp` receives a caller-authored `ModelForwardGraphPolicy`, not a training/inference mode. Phase2 training asks for an autograd-connected retained graph with dropout; Phase2 inference owns the autoregressive generation session and explicitly rebuilds `ModelForwardRequest` / `ModelForwardRuntimePayload` in `training/Phases/Phase2_InferenceLoop.cu` for read-only full-context scoring with detached parameter views and no dropout. `ModelForwardRequest::parameter_registry` is the explicit durable parameter source for registry-migrated bundles such as FFN; forward builds detached or connected per-call views there instead of asking compute layers for cached borrowed parameters. `Forward` must remain a read-only graph primitive over durable model state; only orchestration decides whether the call participates in training or inference.

Inference result payloads such as `GeneratedSequence` belong next to the forward/inference boundary under `Shared/Forward/`, not on `grim_language_model_cuda.hpp`. They are Phase2 inference payload types, not durable model topology.

The model-stats payload and free-function API live in `Common/ModelStats.hpp`, and `computeModelStats(const StartupParameterRegistry&)` lives in `Common/ModelStats.cu`. The implementation reads the registry-owned parameter-group inventory after startup registration and must classify counts from explicit `ParamStatsBucket` metadata written by `ParameterGroupRegistration`. It must not estimate parameter counts from config formulas, compare raw tensor pointers, or re-slice hyperparameters.
