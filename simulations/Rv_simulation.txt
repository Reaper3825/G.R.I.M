1. DEFINITION OF R_v
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  The embedding gradient for token v has two sources (UNTIED architecture):

    grad_emb[v] = Σ_{t : tok(t)=v} grad_encoder[t]        (sparse scatter-add)
    grad_lm[v]  = centered^T @ grad_logits[:, v]           (dense matmul)

  The sparse embedding gradient accumulates via atomicAdd. Each occurrence
  of token v in the batch contributes one scatter-add to row v.

  Define:
    count(v) = number of times token v appears in the batch
    g_v      = per-occurrence gradient contribution to row v

  Then the total gradient pressure on embedding row v is:

    R_v = count(v) · ||g_v||

  R_v determines how fast W[v] moves per optimizer step. A token with 
  high R_v will dominate weight updates regardless of its semantic importance.

  For the LM head gradient (dense path), count(v) does NOT apply — every
  token position contributes equally to every row. But for the embedding
  backward (sparse path), count(v) is the direct driver.

  Combined gradient norm for row v:
    ||grad_W[v]|| ≈ ||grad_lm[v]|| + count(v) · ||g_v_emb||

  The key insight: when count(v) >> mean_count, the sparse term dominates,
  and R_v scales linearly with frequency.

4. COMPUTING R_v = count(v) · ||g_v||
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  The measured row gradient ||grad_W[v]|| combines two sources:
    ||grad_W[v]|| = ||grad_lm[v]|| + ||count(v) · g_v_emb||

  For the UNTIED architecture in this run (tie_embeddings=false):
    - grad_emb and grad_lm are SEPARATE buffers
    - embedding backward scatters into embedding grad buffer only
    - LM head backward writes to LM head grad buffer only
    - Each buffer has its own optimizer state

  after both backward passes have run. The ROW RMS includes BOTH components.

    3. tok262 has high W_rms (batch 28: 0.0236 → already below init,

    4. tok262's argmax dominance comes from its COSINE ALIGNMENT

    5. CollapseTokenDiag batch=39: max_logit[262]=4.91, but W_rms[262]=0.0236
       (BELOW Xavier init 0.0361). Collapse driven by cos(h, W[262])
       increasing, not by weight growth.

  Re-deriving: logit[v,t] = h[t] · W[v]^T = ||h[t]|| · ||W[v]|| · cos(h[t], W[v]) · d_model

    ||h|| ≈ 0.999 (RMSNorm'd)
    ||W[262]|| ≈ 0.0236
    To produce logit = 4.91:
      cos(h, W[262]) = 4.91 / (0.999 × 0.0236 × 768) = 0.271
    This is a HUGE cosine similarity (normal range is ±0.03).

  For a content token at batch 39 (logit ≈ 2.4, W_rms ≈ 0.025):
    cos(h, W[content]) = 2.4 / (0.999 × 0.025 × 768) = 0.125
    tok262's alignment is 2.2× stronger than a typical content token.

8. R_v SENSITIVITY ANALYSIS — WHAT DRIVES R_v?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  R_v = count(v) · ||g_v||

  Two drivers: frequency and gradient magnitude. Which dominates?

  Decomposition via log:
    log(R_v) = log(count(v)) + log(||g_v||)

  For tok36 vs content:
    log(R_36/R_content) = log(838/20) + log(9.3e-4 / 4.3e-5)
                        = log(41.9)   + log(21.6)
                        = 3.74        + 3.07
                        = 6.81  → R_36/R_content = exp(6.81) ≈ 907×

  Frequency contributes:     log(41.9) = 3.74  → 55% of log-ratio
  Gradient norm contributes: log(21.6) = 3.07  → 45% of log-ratio

  BOTH frequency AND gradient magnitude contribute substantially.
  Neither alone explains the 907× R_v ratio.

  Why does ||g_36|| >> ||g_content||?
    ||g_v|| includes atomicAdd accumulation from scatter density.
    838 scatter-adds into the SAME row coherently increase the row norm.
    Each scatter-add vectors may partially cancel OR reinforce:

    ||Σ_t g_t|| ≤ Σ_t ||g_t||  (triangle inequality)
    ||Σ_t g_t|| ≈ √n · ||g_avg||  (if uncorrelated, random walk)
    ||Σ_t g_t|| = n · ||g_avg||    (if perfectly correlated)

    For tok36: 838 scatter-adds → if uncorrelated: √838 ≈ 29× amplification
                                   if correlated: 838× amplification
    Measured: spike_ratio = 21.4× at batch 1 → closer to √n regime
              spike_ratio = 35.0× at batch 10 → partial correlation emerging

  This means the 838 scatter-adds do NOT fully cancel (as they would for
  pure noise). There is partial coherence in the gradient direction,
  likely because space tokens occur in similar contexts (between words).

11. R_v AND THE COLLAPSE FEEDBACK LOOP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  R_v creates a positive feedback loop that accelerates collapse:

  Step 1: Token v has high count(v) in training data
          → R_v is large → ||grad_W[v]|| is large

  Step 2: Large ||grad_W[v]|| → W[v] moves faster
          → W_rms[v] grows → logit[v] increases (via h · W[v]^T)

  Step 3: Higher logit[v] → higher p(v) → model predicts v more
          → lower loss for v (model "learns" v) 
          → MORE gradient signal flows through v in backward pass

  Step 4: More gradient signal → ||g_v|| increases → R_v increases further

  This is the R_v amplification loop:
    R_v ↑ → W_rms[v] ↑ → logit[v] ↑ → p(v) ↑ → grad_signal[v] ↑ → R_v ↑↑

  Evidence from this training run:
    batch  1: tok36 spike_ratio = 21.4×, logit_max = 3.13
    batch 10: tok36 spike_ratio = 35.0×, logit_max = 3.00 (different tokens)
    batch 34: tok262 is_argmax = 337/8192, logit_max = 4.47
    batch 39: tok262 is_argmax = 595/8192, logit_max = 4.38

  The collapse onset at batch 31-34 shows tok262 jumping from background
  noise to 205-337 argmax positions in just 3 batches. This is the feedback
  loop engaging. Once engaged, R_v for the collapsing token grows
  superlinearly until it saturates (model predicts that token everywhere).

  CollapseTokenDiag progression for tok262:
    batch 31: is_argmax = 205/8192 = 2.5%   (onset)
    batch 32: is_argmax = 280/8192 = 3.4%   (+36%)
    batch 33: is_argmax = 417/8192 = 5.1%   (+49%)

  Doubling time: ~5 batches (from 205 to 417 in 2 batches,

  At this rate, tok262 would reach 50% argmax by ~batch 70-80
  (exponential projection), triggering full mode collapse.

12. WHY tok262 COLLAPSES WHILE tok36 HAS HIGHER R_v
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Paradox: tok36 has R_v ≈ 0.78, tok262 has R_v ≈ 0.14.
  Yet tok262 collapses first (by batch 31-39). Why?

  The answer lies in the DIRECTION of the gradient, not just magnitude.

  tok36 facts (space):
    - W_rms[36] at batch 25: 0.0240 (near Xavier init 0.0361)
    - W_rms[36] at batch 38: 0.0240 (NOT growing)
    - Despite receiving the largest gradient (R_v=0.78), tok36's W_rms
      is NOT inflating in this training run window
    - The gradient may be pushing W[36] in a low-rank direction that
      doesn't increase W_rms (orthogonal update, or cancellation between
      the dense and sparse components)

  tok262 facts:
    - W_rms[262] at batch 28: 0.02355 (BELOW Xavier init)
    - W_rms[262] at batch 39: 0.02356 (essentially flat)
    - Yet logit[262] grows: max_logit goes 3.97 → 4.91 in 8 batches
    - This means cos(h, W[262]) is INCREASING, not ||W[262]||
    - The hidden state geometry is rotating toward W[262]'s direction
    - This is a cosine-driven collapse, not a weight-norm collapse

  Implication for R_v:
    R_v measures gradient MAGNITUDE but not DIRECTION.
    A token with moderate R_v can collapse if its gradient direction
    consistently aligns with the hidden state's dominant subspace.
    A token with extreme R_v may NOT collapse if its gradients cancel
    in the cosine-relevant directions.

  R_v is necessary but not sufficient for collapse:
    - High R_v (tok36): necessary gradient energy exists, but direction
      may not align with collapse geometry
    - Moderate R_v (tok262): less total energy, but highly directionally
      coherent → efficient collapse

14. VERDICT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  R_v = count(v) · ||g_v|| quantifies the total gradient pressure on each
  embedding row. It reveals a 907× asymmetry between tok36 and content tokens.

  Key findings:

  1. R_v is dominated by frequency (55%) and gradient norm (45%) in
     roughly equal measure. Neither alone explains the asymmetry.

  2. tok36 (space) has R_v = 0.78 at batch 1, peaking at 1.29 at batch 10.
     This is 907-1320× the gradient pressure on a typical content token.

  3. Despite having the highest R_v, tok36 does NOT collapse first in this
     run. tok262 collapses instead, starting at batch 31. This means R_v
     is necessary but not sufficient for collapse — gradient DIRECTION
     matters as much as magnitude.

  4. R_v correctly identifies which tokens will GROW fastest (tok36's
     W_rms grew 87.5% in the prior full training run). But it does not
     predict which token will achieve argmax dominance, which depends
     on cos(h, W[v]) alignment.

  5. No global regularization (weight decay, gradient clipping) can
     selectively reduce R_v for high-frequency tokens without damaging
     low-frequency content tokens. The R_v asymmetry is inherent to the
     token frequency distribution of natural language.

  6. Effective interventions must target R_v directly:
     a) Frequency scaling of embedding gradients (w_v ∝ 1/√count)
        reduces tok36 R_v by 6.2× while preserving content token R_v
     b) Per-row gradient norm clipping reduces spike_ratio but does NOT
        reduce R_v (count still multiplies through)
     c) Per-row R_v clipping works but is equivalent to token-dependent
        learning rate, risking undertrained frequent tokens

  7. The R_v metric should be logged alongside existing diagnostics
     to detect pre-collapse gradient asymmetry before it manifests
     as argmax dominance.
